## 2. 后端改动

### 2.1 统计分组（`/api/admin/stats/{section}`）

`StatsService.Section` 在原有 `metrics` 之外新增两个聚合形状，仍然**只允许聚合**：

| 字段 | 含义 |
|---|---|
| `series[]` | 序列：`{key,label,unit,points[{key,label,value}],note}`，缺数据的点位补 0 |
| `breakdown[]` | 分组明细：`{key,label,unit,rows[{key,label,value,note}],note}` |

分组口径：

| section | 内容 | 来源表 |
|---|---|---|
| `overview` | 北极星、新增注册、活跃、上传率、失败率、平均耗时、角色确认覆盖率；按日有效报告/新增注册序列；**用户口径**转化漏斗 | `recognition_tasks`、`report_versions`、`users`、`upload_sessions`、`audit_log` |
| `ops` | 处理通数、处理音频总长、平均耗时、队列、失败率、命中句、风险报告/占比、导出成功率与耗时、清理待办/失败、审计事件、额度消耗与预占；**0—23 时段分布**；额度流水、资产类型、OCR 状态、规则命中 Top10 | 同上 + `deletion_jobs`、`export_jobs`、`daily_quota`、`quota_ledger`、`task_assets` |
| `compliance` | 删除请求、按期完成率（≤24h）、删除失败与平均耗时、权限拦截（DENIED）、原件调取留痕、人工角色确认、待确认角色（时点）、已清理原件、**到期未清理**；审计结果分布与数据治理执行表 | `deletion_jobs`、`audit_log`、`recognition_tasks` |
| `violations` | 检出违规通话数（按 task 去重）、检出率、证据条数、单通平均问题数；**按规则分组分布**与按周趋势 | `violations` + `report_versions` + `audit_rule_versions` |
| `growth` | 累计注册、区间新增、活跃、复检率、次月留存、深度用户占比；按日注册序列；用户分层 | `users`、`recognition_tasks` |
| `quality` | 准确率/误报/漏报 → `PENDING`；规则库版本、启用规则数、**距上次更新天数**、角色确认覆盖率与次数 | `audit_rules`、`audit_rule_versions`、`rule_sets`、`audit_log` |
| `finance` | 全部 `PENDING`/`DEMO`，并写清各自缺什么系统 | 无 |

### 2.2 口径纪律（沿用 S12，并补一条）

1. 每个指标带 `sourceTable/timeField/denominator/sampleSize`；
2. **零分母返回 `null`**，界面显示「暂无数据」，不伪造成 0% 或 100%；
3. 没有来源的指标一律 `PENDING`/`DEMO`；**非 `REAL` 的指标不允许带数值**（单元测试强制）；
4. 分组名必须来自数据库（`audit_rule_versions.group_name`），不允许前端自造分类；
5. 序列缺数据的点位**补 0**，而不是让那一天消失（否则图表会骗人）；
6. `LEFT JOIN` 而不是 `JOIN` 关联规则版本：规则版本缺失时证据仍计数为「未知分组」，不静默丢数据。

### 2.3 新增接口：`GET /api/admin/ops/queue`

队列明细带任务号与耗时，属于**个体数据**，因此不放进 INVESTOR 也能读的 `/api/admin/stats`：

- 权限：`ADMIN` / `OPERATOR`（`INVESTOR` 403）；
- 排序：`created_at` 升序，最多 50 条（与 worker 领取顺序一致）；
- 脱敏：任务号由服务端掩码为「前 4 位 + ••• + 后 4 位」；响应不含 `userId`、原文、签名链接。

## 4. 明确仍然不接真的指标

| 指标 | 状态 | 缺什么 |
|---|---|---|
| 渠道结构 / 自然量占比 / 渠道 CAC | 无数据源 | 小程序端 `source` 参数落库（`users`、`upload_sessions` 无渠道列） |
| 投放素材合规率 / 平台拒审次数 | 无数据源 | 素材投放系统 |
| 付费转化率 / MRR / ARR / ARPU / LTV / NRR | 无数据源 | 支付与订阅系统 |
| 单份报告成本 / 毛利率 | 无数据源 | 成本记账表（听悟时长×单价、OCR 次数×单价、存储） |
| 转写准确率 / 误报率 / 漏报率 | 待人工标注 | 抽样 + 人工真值集；`confidence` 不是准确率 |
| 用户申诉率 / 误标类型 | 无功能 | 申诉入口与申诉表都不存在 |

> 补充口径事实：判读环节是**本地规则引擎**（`RuleMatchService` 纯函数 + `TextNormalizer`），
> 没有模型调用成本。因此历史上「规则判读 ¥1.28/份」这一成本项在现有架构下**不成立**。

### 本轮踩到的坑（记录下来，避免重复）

1. 这台机器上 **pi-lens 的 Java 分析不可用**（`Java analysis unavailable — language tools are missing`），所以 Java 侧无法像 TS 那样即时得到诊断，只能靠 Maven 兜底；两次编译失败就是这样漏掉的。
2. 第一次失败：`StatsMapper` 新增的 `LocalDate` 参数缺 `import java.time.LocalDate`。
3. 第二次失败：`StatsService` 有 4 处 `metric()` 调用**漏了 label 参数**（`exportAvgSeconds`、`deletionAvgMinutes`、`avgIssuesPerCall`、`ruleStaleDays`），javac 报的是「实参和形参长度不同」。
4. 第三次失败：测试直接调用别的包下的包级 `AdminOpsController.mask`，改为在 `com.diting.controller` 包内单测，并把上限收敛抽成 `queueLimit()` 以便断言。
5. 结论：**改完 Java 一定要跑一次 `mvn test`**，不要以「逻辑上没问题」代替编译通过。
