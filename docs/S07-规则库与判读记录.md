**结论摘要**：规则库支持版本化 CRUD（修改生成新版本、启停只影响未来集合、集合快照可复算），
判读引擎是纯函数：hit / require / must-have 三种匹配 + 规范化原文位置映射 + 去重计分。

## 1. 规则语义（`RuleMatchService`，纯函数）

| 类型 | 判定 | 证据与高亮 |
|---|---|---|
| `hit` | 指定角色语句包含任一关键词（规范化后精确匹配） | 证据=该句，highlights=关键词在**原文**的 UTF-16 区间 |
| `require` | 触发角色一句命中触发词后，**随后 N 条目标角色发言**内应包含任一应答词 | 未回应时：`sentenceId=null`、`triggerSentenceId=触发句`、证据=触发句、highlights=触发词区间 |
| `must-have` | 指定角色整通话未出现必需词 | 通话级缺失：`sentenceId=null`、无具体句，note 说明缺失项 |

- **窗口按目标角色发言条数计**，其它角色插话不占额度；窗口内出现应答词即通过。
- **错误角色不触发**：触发词出现在非触发角色身上不产生缺失。
- 该角色在通话里根本没出现时，不产出缺失结论，只记说明——避免把「没这个角色」当成违规。
- 引擎不访问数据库、不调用任何模型、不生成 HTML，高亮只给区间（前端自己切片）。

## 2. 规范化与原文位置映射（`TextNormalizer`）

- 全角 ASCII → 半角（含全角大写→小写）、中英标点归一、连续空白折叠为一个空格、英文统一小写。
- **原文一字不改**：规范化只产出副本 + 下标映射，`toOriginalRange` 把规范化区间换算回
  **原文 UTF-16、左闭右开**区间，前端可直接 `slice`。
- 代理对（emoji 等占两个 UTF-16 单元）整体保留，映射不会切进半个字符（RULE-07 用例含 emoji）。
  实现中发现并修掉一个真实缺陷：全角字母转半角后**没有再统一小写**，导致「ＷＯＲＬＤ」匹配不到「world」。

## 3. 计分口径

```text
riskScore       = min(100, Σ 每个命中规则的扣分)     # 同一条规则在一通电话里最多扣一次
complianceScore = 100 - riskScore
riskFlagged     = riskScore >= threshold             # 阈值边界 59/60/61 已覆盖
```

**证据不减**：重复命中仍逐条返回证据与高亮，只是分数不重复扣——这与开发文档 §8
「同规则/同证据去重、保留全部证据」一致（RULE-04 断言「2 条证据、只扣 1 次」）。

## 4. 角色依赖与边界（RULE-09）

> **2026-09-27 变更（目标角色功能隐藏）**：角色确认链路没有 HTTP 入口（`ReportService.saveMapping`
> 未挂路由、`speaker_mapping_confirmed` 只有建任务时写 `false`），角色永远处于未确认状态，
> 按下面的原口径会让 31 条规则里 26 条 role_scope=AGENT 的规则**静默失效**（实测任务 1046：
> riskScore=0、报告反而判「合规」）。现改为：角色**未确认**时（当前恒为未确认）角色范围与触发角色
> 一律按「任意角色」处理，`RuleMatchService.ROLE_TARGETING_HIDDEN = true`；角色已确认时角色限定不变。
> 同时把当前启用 31 条规则的 `role_scope` 统一改成 `ANY`（26 行；备份与逐行回滚脚本见
> `.diting-backup/rule-role-scope-before-hide-20260927-130403.sql`，`trigger_role` 未动以保留触发方语义）；
> 历史记录用后台 `POST /api/admin/recordings/{id}/reanalyze`（仅 ADMIN）按当前规则集重判、追加新版本。
> 下面的原设计保留作为重新启用时的口径，
> 把开关改回 `false` 即恢复（同时后台 `lib/features.ts::ROLE_TARGETING_ENABLED` 一起打开）。

原设计（开关关闭时生效）：

- 角色范围不是 `ANY` 的规则视为**角色依赖规则**；说话人角色未确认时，这类规则**不参与判读**，
  并在结果里以 `skipped` 显式说明「角色未确认，规则未参与判读」，同时写入 notes。
- 通配角色的规则不受影响（未确认角色也能判），这是刻意的：只对「必须区分催收方/客户」的规则设门槛。
- 结论文案引用平台规则名称与版本，不写法律结论（规则说明字段要求必填依据）。

## 5. 规则库（`RuleService`）

| 能力 | 行为 |
|---|---|
| 新增 | 参数校验（类型/角色范围/扣分 0-100/关键词必填；`require` 必须有触发角色、窗口 1-20、应答词）→ 生成版本 1 |
| 修改 | 必须带 `expectedVersion`，落后即 **409**；成功则**新增版本**并把 `current_version` 用条件更新推进（并发修改只有一个成功） |
| 启停 | `DELETE /api/admin/rules/{id}` 只是停用：`enabled=false`，**历史版本不删**，**历史报告引用不受影响** |
| 集合快照 | `snapshotEnabledRules()` 冻结当前启用规则的版本 id 列表到 `rule_sets`，并返回定义；`definitionsOf(version)` 可复算历史判读 |
| 权限 | 读 ADMIN/OPERATOR；写仅 ADMIN（OPERATOR 与用户 token 都被拦，30 项 E2E 里验过） |

版本号推进之所以用条件更新而不是直接 `updateById`：两个并发修改都读到同一个
`current_version` 时，只有第一个能推进，第二个拿到 0 行影响并报冲突，避免“版本号回退”。
