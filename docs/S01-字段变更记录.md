### 2.1 既有表非破坏增列

### 2.2 既有列定义调整（均为放宽或精度对齐，不动语义）

| 表.列 | 变更 | 原因 |
|---|---|---|
| recognition_tasks.status | VARCHAR(16) → VARCHAR(32) | 新枚举 `TRANSCRIBING`/`WAITING_ROLE` 超出原宽度；**值未改写** |
| recognition_tasks.oss_object | NOT NULL → NULL | 对齐开发文档 §6.1 的 `?`；新流程对象 key 以 upload_sessions 为准 |
| recognition_tasks.created_at / finished_at | DATETIME → DATETIME(3) | 对齐文档 DATETIME(3) 约定；已有值按 `.000` 保留 |
| users.created_at | DATETIME → DATETIME(3) | 同上 |

### 2.3 索引变更

新增（8）：`uk_user_idem(user_id,idempotency_key)`、`uk_upload(upload_id)`、`uk_task(task_id)`、
`idx_user_created(user_id,created_at,id)`、`idx_queue(status,next_attempt_at,lease_until)`、
`idx_expiry(expires_at,audio_purged)`、`uk_task_seq(task_id,sequence)`、`idx_task_start(task_id,start_ms)`。

删除（3，均被新索引前缀覆盖，非数据破坏）：`recognition_tasks.idx_user`、`recognition_tasks.idx_task`、`sentences.idx_task`。

顺序保证：**先加新唯一键与索引，后删旧索引**，中途失败不会留下“只删不加”。

### 2.4 约束

- 唯一键（既有表）：`uk_user_idem`、`uk_upload`、`uk_task`、`uk_task_seq`；新表另有 11 个业务唯一键。
- CHECK：`chk_sentences_time(start_ms<=end_ms)`、`chk_rule_deduct(0—100)`、
  `chk_violation_deduct(0—100)`、`chk_report_score_range(分数与阈值 0—100)`、`chk_quota_nonneg(额度非负)`。
- 枚举类（status/role/match_type/state 等）**不建 CHECK**：状态机在 S06 还会演进，用数据库 CHECK 锁死会制造迁移摩擦；
  按开发文档“应用与数据库校验一致”的要求，改由应用层枚举校验，测试用例覆盖合法与非法取值。

### 2.5 新表（14 张，开发文档 §6.2—§6.4）

`upload_sessions`、`speaker_mappings`、`deletion_jobs`、`audit_rules`、`audit_rule_versions`、`rule_sets`、
`report_versions`、`violations`、`app_config`、`daily_quota`、`quota_ledger`、`admin_users`、`audit_log`、`export_jobs`
（另有基础设施表 `schema_migrations`）。共 18 张表；新表排序规则显式对齐既有表的 `utf8mb4_0900_ai_ci`。

## 3. 与开发文档 §6 的口径差异与处理

| 项 | 文档写法 | 实际处理 | 依据 |
|---|---|---|---|
| `sentences.sequence` | `INT!` + `UK(task_id,sequence)` | 实际库原先**没有该列**：新建→按 `(start_ms,id)` 回填→收紧 NOT NULL→加 UK | 文档 §6.1；回填保证 5 行历史句子得到确定句序 |
| `recognition_tasks.oss_object` | `VARCHAR(255)?` | 实际为 NOT NULL，本轮放宽为 NULL | 对齐文档；旧代码仍会写入该列 |
| `export_jobs.created_at` | 单元格写 `DATETIME(3)?` | 按 NOT NULL 实现 | 同表说明“创建时间新记录必填” |
| `recognition_tasks.idempotency_key` | `VARCHAR(64)?历史兼容` | 建列并加 `uk(user_id,idempotency_key)` | 历史行全为 NULL，MySQL 唯一索引允许多个 NULL，无冲突 |
| 日期存 UTC | §6 建议“建议存 UTC DATETIME(3)” | **只对齐精度，不改时区语义** | 现库按 Asia/Shanghai 存本地时间；UTC 化会影响现有读写与展示，需单独立项 |
| 物理外键 | 未要求 | 不加外键，沿用既有表风格 | 文档 §6.4“跨表业务引用必须受事务校验” |
| JSON 列 | `JSON` | 实体用 `String` 承载 | 当前代码库无任何 MyBatis-Plus TypeHandler；S07/S11 若需要再引入 `JacksonTypeHandler` |
| `task_id` 对外命名 | “DTO 使用 remoteTaskId” | **本轮不动 DTO** | 属 API 契约变更，需与两端同步，放 S02（S01 修改范围不含 DTO/前端） |
| 旧状态值转换 | “旧 PENDING/ONGOING 仅按迁移规则转换” | 本轮**保持原值**（证据：状态分布迁移前后一致） | `diting-app/src/types/api.ts` 目前仍是旧枚举；转换必须与 S06 状态机、两端展示同批发布，避免界面回退 |

## 5. 回滚方式

```bash
# 1) 结构与数据按需保留：默认在新表有数据时拒绝回滚
mysql -h127.0.0.1 -u<user> -D diting < diting-server/src/main/resources/sql/migration/V2__S01_rollback.sql

# 2) 确认要丢弃 S01 新表数据时（不可逆）
#    mysql -D diting -e "SET @diting_s01_force_rollback = 1; SOURCE .../V2__S01_rollback.sql"
```

护栏与前提：

- 新表只要有数据就必须显式 `@diting_s01_force_rollback = 1`，否则 `SIGNAL` 中止。
- 若已出现 `oss_object` 为空的新任务，回滚会中止（无法恢复 V1 的 NOT NULL 约束）。
- 回滚会删除 S01 新增列（`sequence`/`words`/租约字段等）及其内容，属预期；回滚后三表结构指纹与迁移前一致（DB-05 已验证）。
