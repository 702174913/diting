# S03 策略配置与额度原子性 · 记录

版本：v1.0 · 日期：2026-09-24 · 阶段：S03
规格依据：[开发文档](./开发文档.md) §6.4 数据字典、§7.3 接口、§8 规则与计分；[开发计划](./开发计划.md) §6 S03。

**结论摘要**：三项策略配置可按版本快照读写，每日额度用「条件更新 + 影响行数」做 CAS，
任务登记与额度预占在同一事务内完成，幂等键与「按上传对象派生」双保险防重复扣费。
验证：**64 项单元/切片测试 + 32 项端到端断言**全部通过，其中并发争份额、跨日隔离、
事务回滚、重复退还都在真实 MySQL 上验过。

## 1. 三项策略配置

| 配置键 | 含义 | 默认初值 | 允许范围 |
|---|---|---|---|
| `daily_free_quota` | 每日免费份数 | 3 | 0—10000，**0 表示没有免费额度，不是无限** |
| `risk_threshold` | 风险阈值 | 60 | 0—100 |
| `max_recording_minutes` | 最长录音时长（分钟） | 10 | 1—600 |

- 三个键作为**同一版本快照**：读取缺行时按默认值补齐（幂等）；保存时三行一起写、版本 +1。
- 保存带 `expectedVersion` 乐观锁：落后于当前版本返回 **409**，不覆盖别人刚改的配置。
- 范围越界返回 **422**，文案直接说明边界（例如“每日免费份数需为 0-10000 的整数”）。
- 上限值（10000 份 / 600 分钟）是防止把配置填成天量值让时长校验形同虚设，属本轮新增的合理约束。

## 2. 额度模型

记账维度是 **(用户, 业务日)**，业务日按 **Asia/Shanghai** 计算（`00:00` 东八区换日，不是 UTC）。

| 计数 | 含义 |
|---|---|
| `reserved` | 已预占：任务已登记、云端尚未确认受理 |
| `consumed` | 已消费：云端确认受理 |
| `remaining` | `max(0, 上限 - reserved - consumed)` |

流水 `quota_ledger` 一个任务一行（`uk_task`），状态机：

```text
RESERVED ── CAS ──> CONSUMED   （云端已受理）
    └──── CAS ──> RELEASED     （确定未被受理，退还）
```

- 所有增减都用**条件更新 + 影响行数**，不做「先查再改」：并发下「看到还剩 1 份」的两个请求
  只有一个能把 `reserved + consumed < limit` 的条件更新命中，另一个拿到 0 行 → 429。
- 状态转换同样用 CAS：影响 0 行表示已被别的请求改过，**不再改动计数**，因此重复消费/重复退还都是空操作。
- 预占必须与任务登记在同一事务内（见下）；确定未被云端受理才允许 `release()`，
  提交结果不确定时保持 `RESERVED` 等 S06 对账，不立即返还又重提。
- `consume()`/`release()` 按**流水所属业务日**回写计数，跨日也不会串账。

## 3. 提交链路的变更（重要）

`POST /api/task/submit` 现在是：

```text
幂等键（客户端提供 / 按上传对象派生）
  → 已存在同一键的任务？直接返回该任务，不重复扣份数
  → 服务端校验时长上限（前端预检被绕过也拦得住，超限 422）
  → 登记任务（status=PENDING）
  → 预占额度（同事务；额度不足 429 并整体回滚）
```

**行为变更**：本轮把「立即调用听悟 CreateTask」从请求路径里移除——它属于 S06 的持久作业管线
（队列、租约、对账），而当前云凭据还是占位值，保留只会让提交必然失败并留下半个状态。
现在提交**不产生云调用**，任务停在 `PENDING` 等待 S06 的作业接管；这一点在验收时按“离线通过”计，
不代表转写可用。

幂等键规则：

- 客户端传了就用客户端的（最长 64 位，超长 422）；
- 没传则按上传对象派生 `auto:<sha256(objectKey) 前 56 位>`，因此**同一个已上传对象重复提交
  只会得到同一个任务**，不会重复扣份数；
- 并发重复提交由唯一键 `uk(user_id, idempotency_key)` 兜底：第二条被拦下后返回已登记的那条任务。

## 4. 接口

| 方法/路径 | 权限 | 说明 |
|---|---|---|
| `GET /api/task/quota` | 登录用户 | `{businessDate, limit, reserved, consumed, remaining, maxRecordingMinutes, riskThreshold}` |
| `POST /api/task/submit` | 登录用户 | 入参 `objectKey`、`durationSec`、可选 `idempotencyKey`；返回 `{id}` |
| `GET /api/admin/config` | ADMIN/OPERATOR 只读 | 三项配置 + `version` + `businessDate` |
| `POST /api/admin/config` | 仅 ADMIN | 入参 `expectedVersion` + 三项配置；冲突 409、越界 422 |

保存动作的审计写入属 S10（`audit_log` 表已在 S01 建好），本轮只做权限与版本控制。

端到端里的关键几条：

- **QUOTA-05**：两个并发提交争最后 1 份 → 一个 200、一个 429，之后 `reserved=1`、`remaining=0`（不超卖）。

- **QUOTA-06**：`START TRANSACTION` 里插入任务并预占后 `ROLLBACK` → 任务数与 `reserved` 双双复原。
- **QUOTA-07**：同一条流水连续两次退还 → 第二次影响 0 行（不重复退还）。
- **QUOTA-03**：昨天已用满不影响今天，业务日按东八区写入 `quota_ledger`。
- **时长边界**：601s 被拒、600s 通过（服务端不再信任前端预检）。

## 6. 决策与偏离

| 项 | 处理 | 理由 |
|---|---|---|
| 云任务提交位置 | 从 submit 移到 S06 持久作业 | 见 §3；避免请求路径里做外部调用 + 不确定状态无法对账 |
| 自动补偿/对账 | 本轮只交付状态机与 CAS 语义，不自动退还 | 判定“是否被云端受理”需要听悟契约与回调（S05/S06） |
| 业务日实现 | `Clock` 可注入（测试用固定时刻验边界） | 跨日逻辑必须能被测试钉住，不能靠“跑的时候正好不在边界” |
| 配置上限 | 份数 ≤10000、时长 ≤600 分钟 | 防运营误填天量值；文档只给了下界与 0—100 的阈值范围 |
| 前端额度 UI | 未做 | 属 S09（小程序闭环）；本轮只提供 `GET /api/task/quota` |
