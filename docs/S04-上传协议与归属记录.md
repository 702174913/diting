# S04 OSS 上传协议与归属 · 记录

版本：v1.0 · 日期：2026-09-24 · 阶段：S04
规格依据：[开发文档](./开发文档.md) §5.1 上传契约、§6.2 上传会话、§11 配置；[开发计划](./开发计划.md) §7 S04。

**结论摘要**：上传协议固定为「服务端签发预签名 + 客户端原始字节 PUT」，客户端再也无法指定
objectKey；`complete` 用服务端测得的事实（存在、大小、文件头格式）复核，客户端声明只作预检；
登记任务只接受本人已验证的 `uploadId`。验证：**78 项单元/切片测试 + 43 项端到端断言 +
4 组前端请求层断言**全部通过。真实云上传（微信真机 + OSS）仍属 S14。

---

## 1. 协议与接口

```text
POST /api/upload/sign     {filename, consentVersion, declaredSize}
  → {uploadId, objectKey, uploadUrl, method:"PUT", headers, expiresAt, cleanupAfter}
客户端 → 按 method+headers 发送**原始字节** PUT（不是 multipart）
POST /api/upload/complete {uploadId} → {status:VERIFIED, sizeBytes, mediaFormat, contentHash, durationMs:null}
POST /api/upload/refresh  {uploadId} → 同一会话的**新签名**（objectKey 不变，用于签名过期）
POST /api/task/submit     {uploadId, declaredDurationSec?} → 登记任务并预占额度
```

- `objectKey` 由服务端生成：`recordings/{userId}/{uuid}.{ext}`，owner 前缀 + 随机名，客户端无法控制路径。
- 同意记录：`consentVersion` 必填（缺失或空白直接 400），版本与同意时间落在 `upload_sessions`。
- 预签名有效期 15 分钟、会话留存 24 小时（`diting.media.sign-ttl-minutes` / `session-ttl-hours`）；
  孤立对象的实际清理属 S13，本轮只登记 `cleanup_after`。

## 2. 校验口径（只认服务端测得的事实）

| 校验项 | 依据 | 说明 |
|---|---|---|
| 对象存在 | `HEAD` | 不存在 → 422「对象不存在，请重新上传」 |
| 大小 | `HEAD` 的 `Content-Length` | 空文件 422；超 `max-size-bytes` 422 |
| 真实格式 | 读前 16 字节做文件头嗅探 | 认出 m4a/mp4/mp3/wav/flac/amr/aac/ogg；与扩展名不一致直接拒绝 |
| 内容指纹 | `ETag` 存 `content_hash` | 供后续比对对象是否被替换 |
| 时长 | **上传阶段不写** | 离线无法可信测量；S05 用听悟返回的 Duration 回填并交叉校验 |

客户端声明的 `filename`/`declaredSize` 只用于提前拒绝（预检），不写入事实字段。

## 3. 归属与状态机

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `SIGNED` | 已签发，未校验 | 重新签名（refresh）、complete |
| `VERIFIED` | 校验通过 | 登记任务（一次） |
| `CONSUMED` | 已用于登记 | 不可再 refresh、不可再登记 |

- 会话是 owner 绑定的：他人的 `uploadId` 在 complete / refresh / submit 三处一律 **404**，不泄露存在性。
- 登记任务时服务端从会话取 `objectKey`，**不再接受客户端直接传 objectKey**（传了就是 400），
  这一条同时把 S03 的 `submit(objectKey)` 契约替换掉。
- 幂等：幂等键默认按 `uploadId` 派生，因此同一上传重复提交只会得到一个任务、一份额度。

## 4. 「上传成功但登记失败」的行为

`UPLOAD-07` 场景（例如时长超政策上限）：事务回滚 → **不产生额度流水**、任务不落库、
会话保持 `VERIFIED` 可立即重试；修正后同一次上传可以正常登记。这条决定了用户不会因为一次误操作
丢掉已上传的文件或白扣一份额度。

## 5. 双端适配

- 小程序 `api/upload.ts`：`sign → uploadRaw → complete → submit(uploadId)`；
  **不再使用 `uni.uploadFile`**（那是 multipart 表单，与预签名 PUT 不匹配）。
  - 微信端：`getFileSystemManager().readFile` 读成 ArrayBuffer 后由 `uni.request` 发原始字节；
    拿不到上传百分比，因此回调 `null`，界面只显示「上传中…」状态（不造进度条）。
  - H5：XHR 直接发送 Blob，用 `upload.onprogress` 汇报真实百分比。
  - 两条路径都不使用 `FormData`，`Content-Type` 严格照用服务端签名时的约定。
- `utils/choose.ts` 增加客户端大小预检（与页面同值，服务端才是权威）。
- `pages/upload/`：上传阶段文案（准备上传/上传中/校验中），H5 才有百分比；失败用服务端 message 提示。

## 6. 目标存储的可插拔性（不改变上传架构）

上传协议没变，但「谁来签发与校验」被抽成端口 `ObjectStorage`，按配置选择：

| 取值 | 行为 |
|---|---|
| `auto`（默认） | 凭据像真实值 → 真实 OSS；否则 `NotConfiguredObjectStorage`（调用即 503 NOT_CONFIGURED） |
| `oss` | 强制真实 OSS |
| `memory` | 内存实现，**仅测试**（启动打 WARN）；配合 `--spring.profiles.active=test` 的写入口做离线全链路验收 |

生产缺凭据时明确 503，不返回看起来成功的假 URL（开发文档 §11）。测试 profile 才允许 mock。
